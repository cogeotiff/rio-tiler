# PR #1079: rasterio reader without WarpedVRT

PR: https://github.com/cogeotiff/rio-tiler/pull/1079 (branch `feat/experimental-rasterio`)

> This work was done by Claude Code under the supervision of vincentsarago.

`rio_tiler.experimental.rasterio.Reader` is a drop-in variant of `rio_tiler.io.Reader` that doesn't use GDAL's `WarpedVRT`. It reads the native pixels of an overview in the dataset CRS, then warps them onto the output grid in memory. It's the "read, then warp" approach first sketched in #656 (which this PR replaces), and the same algorithm as `rio_tiler.experimental.geotiff.Reader`.

It builds on [warp_parity.md](warp_parity.md) (PR #1083, merged): the shared single-pass `warp()`, GDAL's overview rule and per-band nodata handling.

## Why

`rio_tiler.io.Reader` warps on read. It builds a `WarpedVRT` aligned with the output and lets GDAL pick the overview and warp each output pixel. That has two drawbacks:

- **The logic only exists inside GDAL.** Readers that don't use GDAL to fetch data (async-geotiff, Zarr) can't share it, so they can't be checked against the same algorithm.
- **Some reads are slow.** Per-band and mask reads through a `WarpedVRT` built at native resolution miss GDAL's output-size warp and fall into a block-by-block path. On a Sentinel-2 TCI, a z3 tile with `indexes=1` takes 3.11 s of CPU with `rio_tiler.io.Reader` and 0.01 s with this reader.

## Design

```
rio_tiler.io.Reader:               WarpedVRT aligned on the output → vrt.read()           (GDAL does everything)
experimental.rasterio.Reader:      window in dataset CRS → overview read → warp() in memory
```

1. Transform the requested bounds to the dataset CRS and build the source window.
2. Select the overview with GDAL's rule (`rio_tiler._warp.get_overview_level`), from the factor computed like the sync reader (`get_downsampling_factor`).
3. Read the native pixels with `dataset.read(window, out_shape=<overview size>)`. rasterio can't open an overview as a dataset, so requesting an `out_shape` matching the overview makes GDAL read straight from it. Like GDAL, the overview is assumed to cover the full extent (`ceil(size / decimation)`), so the window can have fractional offsets.
4. Warp onto the output grid with `rio_tiler._warp.warp` in a single pass. The kernel is `reproject_method` when the CRS changes and `resampling_method` otherwise.

The read step and the warp step are decoupled, so the read can be swapped for any backend that can fetch a window of pixels.

## What

- **`rio_tiler/experimental/rasterio.py`:** `Reader`, a subclass of `rio_tiler.io.Reader` with the same API.
  - `tile()` / `part()`: steps 1–4 above.
  - `preview()`, `point()` (incl. `interpolate`), `read()` and `statistics()` are re-implemented with the same logic.
  - Opening the dataset (incl. GCPS), `info()` and `feature()` are inherited.
  - Mask handling follows `rio_tiler.reader.read` (nodata, alpha band, internal mask). When the mask comes from a nodata value, the dataset mask isn't read and is rebuilt from the data (same idea as #1074).
  - `buffer` is supported. `padding`, `vrt_options`, `align_bounds_with_dataset` and `minimum_overlap` are ignored with a `UserWarning`. Only `nodata` and `unscale` are taken from `options`.
- **`tests/test_experimental_rasterio.py`:** 33 tests comparing the reader with `rio_tiler.io.Reader` (tiles, masks for nodata/internal mask/alpha datasets, `read()`, `preview()`, `point()`).
- **`docs/src/experimental/rasterio.md`:** both approaches with figures, the remaining differences, a behaviour table and pros/cons. The figures are generated by `docs/scripts/experimental_rasterio/experimental_rasterio_figures.py`.
- **`tests/benchmarks/async_cog_benchmarks.py`:** benchmark for the new reader.

## Investigation: `reproject_method` other than `nearest`

With `reproject_method="bilinear"` or `cubic`, reprojected tiles differ from `rio_tiler.io.Reader`. The async-geotiff reader gives exactly the same numbers, so the gap is in the shared `rio_tiler._warp.warp`, not in this reader's read step.

### Size

`cog.tif`, `warp()` vs `rio_tiler.io.Reader`, both methods `bilinear`:

| zoom | median tile identical | pixels differing | of those within ±1 | mean \|diff\| / mean value | p99 \|diff\| |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 5 | 66% | 35% | 69% | 0.91% | 270 |
| 6 | 80% | 30% | 76% | 0.42% | 162 |
| 7 | 90% | 21% | 84% | 0.18% | 74 |
| 8 | 95% | 13% | 91% | 0.06% | 28 |
| 9 | 100% | 0% | — | 0% | 0 |

Values range from about 1 to 6,900 (uint16). `cubic` is slightly larger, up to 1.2% mean at z5. With `reproject_method="bilinear"` and `resampling_method="nearest"`, the median tile is 98.7% identical or more: GDAL's overview rule then picks a coarser overview (threshold 1.2 instead of 1.0), so the warp downsamples less.

### Cause

GDAL's bilinear and cubic output, when downsampling, depends on how the warp is split into chunks.

- Both readers read the same overview, and GDAL runs the same kernel in every path (`GWKBilinearNoMasksOrDstDensityOnlyUShort`, from `CPL_DEBUG`).
- When downsampling, GDAL widens the kernel (anti-aliasing) and sets it up for each chunk from that chunk's source window.
- The paths chunk differently for a 256×256 tile:

  | path | output chunks |
  | --- | --- |
  | `rio_tiler.io.Reader` (WarpedVRT, `add_alpha=True`) | 2 × 256×128 (VRT blocks) |
  | WarpedVRT without alpha | 1 × 256×256 |
  | `warp()` (`rasterio.warp.reproject`) | 128×128 + 2 × 64×64 |

- UTM→Web Mercator at ~73° latitude has a large scale change across a tile, so the chunk-dependent kernel matters here.
- With `nearest` there's no widened kernel, and the outputs are identical.

### Ruled out

| hypothesis | test | result |
| --- | --- | --- |
| Different overview | GDAL single-pass warp from each overview level | Same level in both readers |
| Two-step read in `io.Reader` | WarpedVRT on the output grid from the overview | Single pass, 100% identical to `io.Reader` |
| Masked arrays in `warp()` | `reproject` with plain / masked / alpha sources and destinations | No change |
| Window cropping at the edges | Source window padded by up to 32 px | No change with `reproject`; small gain with a VRT |
| Missing source pixels around each chunk | `SOURCE_EXTRA` 0, 1, 2, 4 and 16, with a tight and a +16 px window | No change (≤ 1 point); `io.Reader`'s own output is identical for every value |
| Per-chunk scale estimate only | Same explicit `XSCALE`/`YSCALE` in both paths | Still different |
| Approximate transformer | Tolerance `1e-6` in both paths | No change |
| GDAL options | `SAMPLE_GRID`, `SOURCE_EXTRA`, `UNIFIED_SRC_NODATA`, `INIT_DEST`, memory limit, threads | No change |

### What reproduces `io.Reader`

| approach | z5 median / worst | z7 median / worst |
| --- | --- | --- |
| `warp()` today | 66% / 55% | 90% / 58% |
| `reproject` in 256×128 strips | 66% / 55% | 100% / 85% |
| In-memory WarpedVRT (`add_alpha=True`) over the window | 77% / 66% | 100% / 85% |
| WarpedVRT (`add_alpha=True`) over the **whole overview** | 100% / 100% | 100% / 100% |

Only the whole overview reproduces `rio_tiler.io.Reader` exactly. That defeats "read a window, then warp" and isn't possible for async-geotiff, so exact parity isn't a goal. The difference is documented in the docs page, PR #1079 and [warp_parity.md](warp_parity.md). I didn't isolate which other chunk-dependent factor in GDAL's kernel remains once the scale is forced.

## Open items

- **`ImageData.reproject` per-band nodata.** It passes a masked array straight to `rasterio.warp.reproject`, so a pixel that is nodata in one band becomes nodata in every band. That's the bug fixed in `warp()` by #1083. It's used by `preview()` with a different `dst_crs` in this reader and the async-geotiff reader, and it's a public method. Already on `main`; best fixed in a separate PR.
- **Partial fix for the `reproject_method` gap.** An in-memory WarpedVRT with `add_alpha=True` in `warp()` raises the z7 median to 100% but only reaches 77% at z5, and copies the source into a dataset on every call. Not worth it unless exact parity at mid zooms matters.
- **Tests.** `tests/test_async_geotiff.py` passed before the rebase and hasn't been re-run since. The rest of the suite wasn't run locally.
- **CPU times.** Measured before the rebase on #1083 and not re-run.
- **Coverage.** Antimeridian, polar projections and inverted-latitude datasets have limited tests, and performance was only compared on a few datasets.
